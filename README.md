## Задание 1. СУБД

### 1.1. Бюджетирование, финансовые отчёты, прогнозирование рисков
Лучше всего подойдёт **реляционная OLTP-СУБД**: PostgreSQL, MS SQL Server, Oracle.  
Почему: нужны строгая схема, ACID-транзакции, внешние ключи, ограничения целостности, роли и аудит. Для бюджетирования важна предсказуемость и непротиворечивость данных.

Для аналитических отчётов и прогнозирования рисков лучше добавить отдельный аналитический слой: **MPP/колоночную СУБД** — ClickHouse, Greenplum, Snowflake, Vertica — или data lake + Spark.  
Итог: OLTP-реляционная СУБД для бюджета, OLAP/MPP или lakehouse для аналитики и ML-прогнозов.

### 1.1.* Хеширование стало занимать длительное время
Зависит от того, что именно хешируется:
- для криптографического хеширования — **OpenSSL EVP/libcrypto** с аппаратным ускорением SHA-NI;
- для некриптографического — **xxHash, MetroHash, CityHash**;
- если речь о hash join/hash index в СУБД — включить параллельные планы, увеличить `work_mem`, использовать hash-индексы, партиционирование;
- для тяжёлых вычислений — GPU-API: **CUDA/OpenCL**.

### 1.2. Лендинги и CRM
Для лендингов хорошо подходит **документная NoSQL-СУБД**: MongoDB, DynamoDB, Couchbase.  
Причины: гибкая схема, быстрая запись заявок, простое масштабирование, разные наборы полей для разных проектов.

Для CRM можно использовать:
- **PostgreSQL с JSONB** — если важны связи, транзакции, отчёты, целостность;
- **MongoDB** — если CRM должна быть максимально гибкой и быстрой, а сложные связи не критичны.

Оптимальный вариант: лендинги — MongoDB/DynamoDB, CRM — PostgreSQL с JSONB.

### 1.2.* Можно ли закрыть одной СУБД?
Да. Лучший компромисс — **PostgreSQL с JSONB**:
- JSONB хранит гибкие данные лидов;
- обычные таблицы — сделки, клиенты, воронка, задачи;
- GIN/B-tree индексы, полнотекстовый поиск, партиционирование;
- при росте — Citus, PgBouncer, репликация.

Альтернатива — **MongoDB в replica set/sharded cluster**: одна СУБД и для лендингов, и для CRM, если CRM не требует сложной реляционной логики.

### 1.3. База корпоративных норм, правил и обучающих материалов
Подойдёт **документная СУБД** — MongoDB, Couchbase — или **PostgreSQL с расширениями** `ltree`, `tsvector`, `JSONB`.  
Структура: разделы, подразделы, статьи, версии, вложения, права доступа.  
Документная модель удобна, потому что материалы могут иметь разную структуру.

### 1.3.* Можно ли использовать существующую СУБД?
Да. Если уже есть PostgreSQL, лучше сделать отдельную схему `knowledge_base`:
- `sections` — иерархия через `ltree`;
- `articles` — текст, версии, автор, статус;
- `attachments` — ссылки на S3/файловое хранилище;
- полнотекстовый поиск через `tsvector`;
- RBAC для доступа по подразделениям.

Если уже есть MongoDB — использовать коллекции `sections`, `articles`, `attachments`.

### 1.4. Логистика: маршруты, курьеры, документы
Для быстрой работы со связями лучше всего подходит **графовая СУБД**: Neo4j, ArangoDB.  
Но если важна геомаршрутизация, часто эффективнее **PostgreSQL + PostGIS + pgRouting**.  
Тогда:
- объекты, склады, курьеры, маршруты, документы — таблицы;
- геометрия и маршруты — PostGIS/pgRouting;
- связи между рейсами, курьерами и документами — обычные FK и графовые запросы через рекурсивные CTE.

### 1.4.* Можно ли подключить отдел закупок?
Да, если логистика работает на PostgreSQL/PostGIS. Тогда закупки можно вынести в отдельную схему `procurement`: поставщики, договоры, заявки, заказы, счета, оплаты.  
Если логистика на Neo4j, то закупки лучше оставить в реляционной СУБД, а интеграцию делать через API/ETL.

### 1.5.* Можно ли все задачи решить одной СУБД?
Технически да — **PostgreSQL с расширениями**:
- JSONB — лендинги, CRM,知识 base;
- PostGIS + pgRouting — логистика;
- ltree + tsvector — иерархия и поиск;
- Apache AGE — графовые запросы;
- Citus — шардирование и масштабирование;
- TimescaleDB — временные ряды;
- pg_partman, pg_trgm, pgcrypto — дополнительные возможности.

Но на практике для больших аналитических и ML-нагрузок лучше использовать полиглот-архитектуру: PostgreSQL + ClickHouse/Spark + MongoDB/Neo4j там, где они действительно эффективнее.

## Задание 2. Транзакции

### 2.1. Пополнение баланса телефона: шесть шагов
1. Пользователь инициирует пополнение: вводит номер, сумму, подтверждает платёж.
2. Система проверяет корректность номера, сумму, лимиты, аутентифицирует пользователя.
3. Создаётся транзакция со статусом `pending`, проверяется достаточность средств и выполняется резервирование суммы.
4. Платёжный шлюз отправляет запрос оператору связи/биллингу на зачисление средств.
5. Биллинг оператора зачисляет деньги на лицевой счёт абонента и подтверждает успех.
6. Банк/платёжная система списывает зарезервированные средства, транзакция переводится в `completed`, пользователь и оператор получают уведомление; при ошибке выполняется откат/возврат.

### 2.1.* Автоплатёж
1. Наступает триггер: дата, расписание или баланс ниже порога.
2. Система проверяет правила автоплатежа, согласие пользователя, лимиты и доступность средств.
3. Создаётся идемпотентная транзакция, средства резервируются.
4. Запрос отправляется оператору связи/биллингу.
5. Оператор зачисляет средства и подтверждает операцию.
6. Средства списываются, статус обновляется, пользователь уведомляется. При ошибке — повторные попытки по регламенту, затем уведомление и возможное отключение автоплатежа.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL-систем
1. **ACID-транзакции** и строгая согласованность.
2. **Строгая схема и целостность**: внешние ключи, ограничения, нормализация.
3. **Мощный SQL**: JOIN, агрегации, оконные функции, сложная аналитика.
4. **Зрелость и стандартизация**: много инструментов, администраторов, практик.
5. **Безопасность и управление доступом**: роли, права, аудит, шифрование.

### 3.1.* Преимущества NewSQL
NewSQL сочетает лучшее из SQL и NoSQL:
- SQL-интерфейс и ACID;
- горизонтальное масштабирование;
- автоматическое шардирование и репликация;
- распределённые транзакции;
- высокая доступность и geo-distribution;
- меньше компромиссов между согласованностью и масштабом.

Примеры: CockroachDB, TiDB, YugabyteDB, Google Spanner.

## Задание 4. Кластеры

Критерий выбора типа СУБД:
- характер нагрузки: OLAP, batch, ML, streaming;
- объём и скорость роста данных;
- требования к latency и throughput;
- нужна ли строгая согласованность;
- отказоустойчивость и стоимость;
- удобство масштабирования на 1000 машин.

Для большого количества вычислений над огромными данными лучше всего подходит **распределённая data-parallel модель**:
- **MPP** — для SQL-аналитики: ClickHouse, Greenplum, Snowflake;
- **MapReduce** — для классической batch-обработки;
- **DAG-модель Apache Spark** — чаще всего оптимальна: in-memory, итеративные вычисления, отказоустойчивость через lineage, работа на YARN/Kubernetes, данные в HDFS/S3.

Почему: данные партиционируются, вычисления идут параллельно на 1000 машинах, computation переносится к данным, потерянные задачи пересчитываются. Для чистой SQL-аналитики лучше MPP, для сложных вычислений и ML — Spark/DAG.
